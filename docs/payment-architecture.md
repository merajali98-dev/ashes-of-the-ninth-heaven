# Future wallet purchases and settlement architecture

Status: **adapter implemented, real checkout disabled**. `js/payments.js` makes no network request, creates no provider, reads no browser wallet, signs nothing, and changes no game currency on import. The existing game remains local and free to play. The storefront is a review of proposed offers, not a payment processor. No chain, token contract, merchant address, keys, or paid balances are configured.

## Products and economy boundary

`PURCHASE_PACKS` contains five Jade packs (100 / 500 / 1,000 / 2,500 / 5,000) proposed at $1 / $5 / $10 / $25 / $50 USD. Three Star Silk packs propose 100 / 500 / 1,000 cosmetic units at $1 / $5 / $10. There are no bulk-rate multipliers, first-purchase multipliers, random contents, automatic renewals, or time-limited purchase pressure in this catalog. `proposed: true` is part of every offer. These are design prices, not promises of production availability, taxes, crypto amounts, or permanent pricing. Star Silk spending and entitlements require their own future cosmetics catalog.

Jade already buys power-bearing cards and crafting inputs. Purchased Jade therefore accelerates acquisition and can indirectly cultivate pets by buying feeding cards. Do not market this as purely cosmetic or as blocking paid pet progression. Cultivation-level gates and earned hero essence should remain meaningful. Paid currency is closed-loop game value: no cash redemption, player transfers, trading exchange, or investment claim. An in-game unit must not be represented as a withdrawable on-chain asset merely because a wallet pays for it.

The existing browser save is deliberately **not** a purchase ledger. Editing or importing it can alter Jade, cards, materials and battle rewards. Paid balances, purchased inventory and premium spending cannot safely launch while those inputs remain client-authoritative. A server balance alone is insufficient: the server must also own all acquisition, spending, salvage, equipment/crafting and reward paths that can exchange purchased value. Local/offline chronicles must be a separate entitlement namespace, with no import path that creates paid ledger entries. Existing offline progress can remain playable; any online migration needs a stated, capped, nonfinancial onboarding policy.

## Adapter API

```js
import {createPaymentAdapter, PURCHASE_PACKS} from './payments.js';
const checkout = createPaymentAdapter(); // always unavailable; safe today

// Future integration only, after the backend and wallet connector exist:
const future = createPaymentAdapter({enabled:true, backend, wallet});
await future.quote('jade-pouch');
// Show quote, fiat price, exact network/token/recipient and fee disclosure.
await future.createOrder({quoteId:'server-quote-id', idempotencyKey:'stable-client-intent-id'});
await future.connectWallet(); // an explicit user action, never on page load
await future.submitPayment(); // explicit confirmation; wallet presents its own fee
await future.refreshOrder(); // server settlement, not wallet optimism
```

Every async method returns `{ok, reason?, state}`. `getState()` returns a detached snapshot. `cancel()` aborts local work and invalidates stale responses, but cannot cancel a blockchain transfer or merchant order. `invalidateWallet()` does the same and clears the account; bind future connector account/chain/disconnect events to it. Existing order details remain available for reconciliation. `disconnect()` serializes the provider disconnect so an older disconnect cannot tear down a newly opened session. No object in this module receives a game or save reference, and no settlement method increments local Jade.

The backend dependency implements `quote({packId,signal})`, `createOrder({quoteId,idempotencyKey,signal})`, `getOrder({orderId,signal})`, and `submitTransaction({orderId,transactionId,signal})`. The future wallet dependency implements `connect({signal})`, `getSession({signal})`, `sendPayment({account,payment,signal})`, and `disconnect()`. It must not request seed phrases or arbitrary token approvals. Asset/network/address validity is chain-specific and belongs to that connector and backend allowlist; a generic adapter string check does not establish a valid address or safe token contract.

Quotes bind `{id,packId,priceCents,currency,amount,expiresAt,payment}`. Payment binds `{network,asset,tokenAmount,decimals,recipient}`. Prices use integer USD cents; token quantities use bounded positive decimal strings, never floating point or exponent notation. Networks use namespaced IDs (for example `eip155:8453` as an illustrative test identifier, **not a selected launch network**). The adapter limits a valid quote to at most fifteen minutes, rejects expired quotes before send, checks the current account and network again, and binds an order retry to its original idempotency key even after a transport failure.

The crypto amount is a server quote, not a browser USD conversion. Before a future launch, server quotes must separately expose merchant fees, taxes where applicable, exact token base units and the estimated network fee. A wallet's network fee may vary and is separate from the merchant payment amount: do not label pack price as a guaranteed all-in total. Display updated wallet fees before final signature. Do not attempt to add a browser-estimated gas amount to the merchant transfer.

After a send is attempted, the adapter refuses a second send for that order even if the wallet result or HTTP notification is lost. A submitted transaction reference is retained when available; it is not proof of payment. Reload recovery must come from the backend account's pending-order list, never a local cache as the authority. Production recovery should explicitly identify replacement, reverted, underpaid, late and wrong-network transfers before permitting a new order.

## Required production services

1. **Account and session service.** Authenticated user identity, authorization on every order/status/balance endpoint, CSRF protection for cookie sessions, secure cookies and session rotation, rate limits, audit logging, account recovery and a separate merchant administration role. A wallet connection does not authenticate ownership by itself. If wallet login is chosen, use a server-issued single-use domain/chain/time-bound nonce and verify the signature server-side; never reuse a login signature as payment authorization.
2. **Product and quote service.** Versioned immutable product snapshots, server-owned prices, supported jurisdictions, chain and token-contract allowlists, validated merchant treasury, decimal/base-unit encoding, configured confirmation policy, expiration and fee/tax disclosures. Currency conversion is bounded, timestamped and obtained from a selected payment provider; no assumption that a stablecoin always equals exactly one dollar. Rate-limit small orders that would be dominated by network fees; block unsupported networks instead of sending an automatic bridge transaction.
3. **Order database.** Durable unique `(account_id,idempotency_key)` and `(account_id,quote_id)` constraints, quote/product/payment snapshots, order ownership, status revisions, expected amount/network/asset/recipient, received amount, provider reference, chain transaction/log index, settlement block and confirmation depth. Retrying the same intent returns the same order; a reused key with a changed payload is a conflict. Use database transactions and row locks/CAS for state changes. Client idempotency is defense in depth only.
4. **Settlement worker.** A signed, replay-protected webhook or a trusted RPC/indexer verifies chain ID, token contract, recipient, base-unit amount, transaction success, event/log identity and required confirmations. The RPC endpoint and merchant recipient never come from a client-provided arbitrary URL. A transaction hash alone, wallet callback, screenshot, browser `fulfilled` JSON or client-declared balance is never accepted. Wrong/partial/late transfers enter support/reconciliation states; they do not auto-credit. Detect provider retries, replacements and chain reorganizations; pending confirmation is not fulfillment.
5. **Append-only currency and entitlement ledger.** Post settlement and grant exactly once in one database transaction, with unique order grant and chain-event indexes. Track purchased and earned provenance as separate ledger lots even if the UI shows a combined Jade balance. Every spend is atomic against the authoritative balance and inventory; forbid negative balances and duplicate mission claims. Refunds and administrative corrections are compensating entries with reason and actor, never edits to historical entries. Star Silk cosmetics should be idempotent, account-bound entitlements with an explicit duplicate-ownership rule.
6. **Reconciliation and support.** Scheduled independent reconciliation compares provider/RPC receipts, orders, grants, spends, refund liabilities and ledger totals. Dead-letter uncertain webhooks, alert on unmatched transfers, and retain searchable receipts/order IDs for support. Define finality/reorg compensation, lost-account assistance and unspent/spent premium refund handling before enabling checkout. Never silently erase earned progression as a refund shortcut. A client cancel must not issue a refund automatically. Recovery after browser reload uses authenticated server state.
7. **Operations and release review.** Secret management, least-privilege treasury and provider access, signed configuration, TLS, backups and restore drills, incident pause switch, audit retention, monitoring, load tests, fraud controls and purchase limits. Tax, refund, sanctions, age/consent and consumer disclosures depend on launch regions and provider; obtain current specialist review before real-money launch rather than claiming this technical adapter satisfies them. Choose an appropriate licensed payment provider and networks only then.

## Order state machine

`awaiting_payment → submitted → confirming → fulfilled`, with permitted direct authoritative jumps when a poll misses intermediate states. Unpaid orders may become `expired`, `cancelled` or `failed`. Confirmed purchases may progress to `refund_pending → refunded`; a declined refund may return to `fulfilled`. Terminal failures cannot silently return to unpaid. The backend must handle its finer-grained support, reorg and underpayment states and map them conservatively into this UI contract.

`fulfilled`, `refund_pending` and `refunded` require a matching server receipt `{ledgerId,orderId,currency,amount,settledAt}`. This shape check prevents accidental client integration errors; it is **not cryptographic verification of arbitrary injected backend code**. Actual trust comes from the authenticated production service and its immutable ledger. All balances and receipts shown to a player must come from that service.

## Verification and remaining work

Primary protocol references for the future connector are [EIP-1193](https://eips.ethereum.org/EIPS/eip-1193) (provider requests and account/chain/disconnect events) and [EIP-4361](https://eips.ethereum.org/EIPS/eip-4361) (domain, chain, nonce and time-bound wallet authentication). Those standards inform a possible EVM implementation; the generic adapter does not import an EVM SDK or commit to that ecosystem. [Coinbase's API conventions](https://docs.cdp.coinbase.com/api-reference/v2/conventions) illustrate string monetary amounts and idempotency for future provider evaluation, without selecting that provider.

`node --test tests/payments.test.js` exercises disabled/no-side-effect behavior, pack math, strict quantities, backend receipt requirements, quote/order binding, idempotency after ambiguous failure, stale responses, account/network changes, expiry, cancellation during an ambiguous wallet send, and failed broadcast notification recovery. Independent QA audits the boundary and storefront. No real wallet/network, payment processor, account service, tax engine or authoritative gameplay backend is implemented or enabled by these tests. The default must remain disabled until those production requirements and an end-to-end testnet settlement/refund/reconciliation suite pass.
